# 数据文件组织规则

本工程中 JSON 数量很多，但它们属于性质完全不同的几类。
判断一份数据该放哪里、能不能和别的合并，看的是**谁写、什么时候变、坏了谁遭殃**，
而不是内容看起来像不像。

## 五类

| 类别 | 谁写 | 谁读 | 例子 | 进 git |
| --- | --- | --- | --- | --- |
| 配置 | 人 | 程序 | `configs/hardware.*.json` | 是 |
| 规则（schema） | 人 | 程序 | `configs/schema/*.json` | 是 |
| 溯源 | 人 + 工具 | 人 | `models/provenance.json` | 是 |
| 结果 / 证据 | 程序 | 人 | `*.summary.json`、`*.report.json` | 否 |
| 流式日志 | 程序（追加） | 人 + 程序 | 所有 `.jsonl` | 否 |

## 为什么不能合并成一个文件

**写入冲突。** 结果文件由程序在运行时写，配置由人手改。放同一文件，
跑一次实验就把刚改的标定值冲掉。

**生命周期打架。** 配置要长期稳定、进版本控制、改动需审；
结果是一次性的、只增不改、按实验目录归档、不进 git。合并意味着两条规矩二选一。

**JSONL 在物理上不能合成 JSON。** 串口日志边跑边追加，进程崩了前面写的还在。
若是一个完整 JSON 对象，写到一半崩溃整个文件就废——而进程崩溃恰恰是最需要日志的时刻。

**失败记录会被覆盖。** 结果文件名带纳秒时间戳（如
`native_j1_1789546152444180900.json`）是故意的。`docs/EXPERIMENTS.md` 规定
「保留失败和中止日志，不能把有日志的测试都算成成功」。写进同一文件会让后一次
覆盖前一次，失败记录随之消失。

## 配置与 schema 的区别

- **profile 是数据**：J2 的下限是 −75 度
- **schema 是规则**：一份 profile 必须有 `lower_rad`，它必须是 6 个有限实数

schema 让规则从 Python 代码里抽出来变成可读的声明，好处是新增字段不用改代码、
任何语言都能校验、一次能报出全部格式问题而不是只报第一个。

## 文件名携带状态

`hardware.unverified.json` 这个名字本身说明它不能用来驱动实机。
`configs/README.md` 明确要求不得把它改名成已验证配置。
M3 产出的标定档案叫 `hardware.dummy_v2.calibrated.json`，写新文件，不覆盖。

profile 文件名中的版本号（`hardware_profile.v2.json`）用于让程序判断
手上这份档案按哪版规则填写、是否需要迁移。标定值是用实机时间一轴一轴量出来的，
不该因为结构升级而作废。

## 新增数据文件时

问三个问题：谁写它、它多久变一次、它被覆盖了谁会受损。
答案不同的数据，放不同的文件。
