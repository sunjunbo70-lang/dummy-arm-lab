# 实机控制源码复核

## 后续实测更正：未验证实体运动

在用户通过 DummyStudio 复位至 [0,0,90,0,0,0] 后，独立程序实际发送了 J1=10° 的位置目标。串口原始回复出现 `15ok\r\n\r\n`，最初被只接受纯数字的队列应答解析器误判为超时；已修复并加入回归测试。源码 Respond 将正文与换行分两次 process_bytes 发送，不同线程的回复可能交错，与此现象相符，但不能据此解释全部异常反馈。

之后记录到 J1 报值从 0.72° 增至 1.80° 并停滞，另有一帧 J3 从 90° 报为 10.07°，程序发送 STOP 并获应答。用户现场确认机械臂没有可见运动，仅电机指示灯闪烁。因此这些数值只能标记为控制器报告值，不能作为实机关节运动成功的证据。此次位置执行测试未通过，不能宣布控制闭环已跑通。

当前可证实的是 USB 主控命令应答；不能从应答推断 CAN 执行、传动运动或实际角度正确。继续定位时应比较同一设备上 DummyStudio 的完整成功交互与独立程序的原始收发，而不是继续放大角度、电流或限位。暂不继续实机运动测试。

## 结论

用户确认实机使用已提供工程设置，并已通过 DummyStudio 验证传动与运动。该信息作为项目依据保留；但工程内部不同文件的参数并不一致，不能选用较宽范围来代表已验证实机限位。

截至本次复核，独立程序已验证角度查询、START 和 STOP 应答。两次带运动意图的测试均在启动检查阶段退出，没有发送 `&` 位置目标。因此尚无独立程序位置指令执行失败或转矩不足的证据。

## 已确认的控制语义

1. 模式 2 为可中断目标点模式。`!START` 调用 SetEnable(true)。周期任务在使能时持续发送 targetJoints，可能恢复已有目标。此前程序在 START 后才检查姿态，会在新目标尚未发出时发生动作。这是测试流程缺陷。
2. 未使能时，档案周期任务仍调用 UpdateJointAngles。因此不能直接认定使能前角度必然陈旧；实际固件缺少每轴时间戳，仍无法用静态重复读数证明反馈新鲜。
3. MoveJ 检查所有六轴目标。任何一轴越限都会使其返回 false；上层命令处理未检查该返回值，仍可返回 ok。FIFO 空间和 ok 都不是运动成功证据。
4. MoveJ 对全部零位移的输入有 maxAngle=0、time=0 的除零风险。EmergencyStop 会调用以 currentJoints 为目标的 MoveJ，因此其数值处理也需审计；STOP 应答不能视为物理停止或驱动断电的证明。当前不刷写固件、不自动修改原工程。
5. 第七个速度参数经过 jointSpeedRatio 和减速比计算，不能直接标成关节 deg/s；旧 Python 适配器的 command_speed_deg_s 命名可能误导。

## DummyStudio 实际位置指令

静态分析原 `DummyStudio_Data/Managed/Assembly-CSharp.dll` 的 `SetSliderBehaviors`：拼接 `&`、六个四舍五入到两位小数的角度、逗号分隔，末尾逗号加换行，然后调用串口 Write。没有附加数值速度字段，固件 sscanf 因而得到六个数，沿用既有速度。

本地分析脚本为 tools/inspect_studio_il.ps1，输出 outputs/studio_control_il.txt。没有执行程序集控制方法。滑块发送格式已确认；完整启动按钮事件可能存储于 Unity 场景序列化数据，本次程序集分析没有恢复完整启动顺序，不宣称已与 DummyStudio 完全一致。

## 后续控制条件

首先解决初始状态与目标同步，明确使能状态、命令模式、目标和停止行为。在模式 2 的档案源码中，未使能时可解析并更新目标，但当前协议没有可靠的目标寄存器读回确认，且无法只凭 ok 判定目标合法。不能未经核对就把“先发目标再 START”当作已验证修复。

逐轴 10° 测试使用原有驱动力，目标需落在已核对配置的共同范围内，并用返回的实际角度与现场观察确认。当前姿态 J2=−75°、J3=180° 时，即使只改变 J1，六轴目标仍包含 −75°；按档案固件会被拒绝。这应先通过已验证的 DummyStudio 移至共同范围内部的测试姿态，再接管，或确认实际固件不同的限位行为。不能仅放宽电脑端阈值，也不能以提高电流替代协议验证。
