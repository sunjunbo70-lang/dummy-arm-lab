研究备忘录更接近现有硬件项目；学习计划可作为概念入门材料，不能直接当部署清单。

需要修正的具体认识：

1. VLM-based 与 diffusion/flow 不是互斥的分类维度。前者描述视觉语言主干，后两者描述动作生成方法，可以出现在同一个系统中。
2. RT-2→Octo→OpenVLA→π₀→InternVLA-M1 不能理解成简单的版本升级或继承链。
3. 连续动作输出不自动保证实机平滑；时间同步、动作块切换、控制延迟和电机能力都会造成抖动。
4. RL 微调不必然提高平滑性。只惩罚 Jerk 容易得到“少动甚至不动”的策略，必须同时约束任务成功、耗时与动作幅度。
5. 5–10 条演示可以验证数据加载、梯度更新和过拟合能力，不能据此证明任务泛化。
6. RLDS 不是所有 VLA 的唯一必需格式。openpi 和 Wall-X 官方流程均有 LeRobot 数据入口；先保存完整原始数据，再做目标框架转换。
7. 人体动作不能仅转成六轴 CSV 就视为机器人训练数据；还需视角一致的视觉观测、机器人可达性、接触/夹爪语义及时间对齐。
8. SAM2 掩码能提供对象区域，不直接提供深度、接触力或可执行抓取姿态。覆盖率也不能替代任务成功率。
9. 一周适合建立认知并完成一个软件闭环，不能承诺完成硬件标定、数据采集和可靠 VLA 部署。
10. 学习计划的 LeRobot 视频链接为 `(c)`，属于明显失效占位；安装命令、模型权重和依赖需要按固定版本重新整理。

### 反馈链路：有基础，但缺少新鲜度证明

历史源码的链路为：CAN `0x23` → `UpdateAngleCallback` → 电机转数除以减速比、转换角度并处理方向 → `currentJoints = motor.angle + initPose` → `#GETJPOS` 返回六个数。

这说明该源码有来自电机的反馈路径，不能一概称为“命令回显”。但 USB 查询返回的是主控缓存：没有每轴采样时间、有效位、CAN 超时标记。新收到一行 USB 响应，不代表六个关节都刚更新；静止数值相同也不能判断失联。可靠方案需要在匹配固件里暴露每轴最近更新时间/序号/有效位，或者用已证实等价的诊断机制。

此外，这是电机侧经减速比换算的关节估计；减速器回差、结构挠曲仍可能导致末端偏差。`#GETLPOS` 来自 FK 计算，不能当独立末端测量工具来证明自身运动学正确。

### 参数存在真实冲突

DEMO YAML 关节下限为 `[-170,-75,0,-180,-100,-720]`；已读历史 REF 构造函数为 `[-170,-73,35,-180,-120,-720]`。连杆常数也不同：旧 RoboDK 配置出现 126.5、117、75.55 mm，而读取的 REF 构造函数出现 109、115、72 mm 等对应机构参数。坐标定义还需逐项核对，不能混拼为一套真实参数。

因此必须建立“参数→来源版本→实际测量→验证人/日期”表；不能选择看起来更宽的限位。手册描述与实测若冲突，应暂停裁决、核对硬件批次，而不是把手册优先级理解成忽略实际证据。

## 5. 建议采用的最小架构

```text
相机 + 关节反馈 + 夹爪状态 + 语言任务
                    ↓
          时间同步 / 观测有效性检查
                    ↓
       BC / ACT / VLA 策略或人工示教
                    ↓
   动作解码 / 反归一化 / 时序调度
                    ↓
  安全控制：限位、限速、增量、时效、故障
                    ↓
              统一 Robot API
          ┌─────────┴─────────┐
       仿真后端             USB 后端
   一个主仿真器          REF → CAN → 电机
          └─────────┬─────────┘
               实测/模拟反馈
                    ↓
          数据记录 / 评估 / 故障分析
```

ROS 2/MoveIt 作为需要规划、TF 和多传感器集成时的桥接层，和直接 Python 接入共用 Robot API；不要维护两个互相绕过安全控制的串口写入者。物理停止通道独立于策略进程，设备失联时不能依赖往已断开的 USB 再发 `!STOP` 来保证停止。

**不用先做完整数字孪生，才能开始模仿学习。** 第一轮真实数据 BC/ACT 的必要条件是可靠反馈、受限执行、同步数据和任务评估。高精度动力学、Genesis 大规模并行、RL 可以后置。ROS 2 有价值，但不是所有学习算法的强制前置依赖。

### Robot API 的设计契约

| 接口 | 必需语义 |
|---|---|
| connect() | 打开连接，不自动使能/回零/标定 |
| get_state() | 返回 q、接收时间、反馈来源、每轴有效性/新鲜度；没有的传感量明确 unavailable |
| enable() | 显式动作，前置条件全部满足 |
| send_action(action) | 校验 schema、单位、顺序、范围、时效，返回接受或拒绝原因 |
| stop() | 按已验证停止策略执行，返回状态；不等同物理急停 |
| disconnect() | 可预测地释放资源，不把无条件断使能当所有姿态都安全 |

统一内部关节单位建议 rad，笛卡尔位置 m、时间 s；USB 的 degree/mm 在适配层转换。初期动作采用六轴关节目标；若夹爪已验证，再加夹爪通道。夹爪是角度、开度、归一化命令还是二值开合，必须显式声明。

不要在主机重复应用 REF 已经做过的减速比和符号变换。需要区分原始电机空间、固件关节空间和算法规范空间。

状态至少保存 `q_measured、t_rx、source、valid_mask、profile_id`；命令至少保存 `q_requested、q_applied、command_id、issued_at、expires_at`。q_applied 表示限幅后提交给驱动的目标，不代表机械上已经执行到位。相机时间与控制时间的偏移需有记录。

## 7. 按验收条件推进的开发顺序

### 阶段 A：只读链路和硬件画像

实现最小串口诊断器，仅查询和记录。记录主控/驱动版本、端口识别、实际响应帧、每种命令模式、通信时延分布、反馈更新行为。若无法读取版本，保留发布包/固件哈希、烧录记录、板卡照片与来源对应关系。

验收：不自动使能；稳定解析六轴反馈；半包、超时、日志混入不造成错帧；能明确区分未知/陈旧状态；确定目前可读的量。电流、温度、错误码没有可用接口时不能填零冒充正常。

建议先用 10 分钟静态记录做基本稳定性检查，再逐步测 5/10/20 Hz 查询能力；这些是测试候选值，不是已确认的设备规格。记录 p50/p95/p99 延迟、超时率、各轴年龄和缺失情况。读超时 1 s、ACK 2 s 是当前配置值，不应自动作为策略运行时的容错预算。

### 阶段 B：统一 API 和低速受限执行

完成六轴方向、零位、可用范围、线缆约束和工具参数表；增加连接、只读、待使能、运行、故障、停止状态机。未知参数阻止运动。先离线录包和模拟传输故障，再由现场人员执行受控单轴验证。

验收：实际初始姿态与目标之间的过渡受限；反馈失效停止新动作；断连/重连不会自动恢复旧轨迹；状态错误能追溯；软件停止和物理停止分别验证。下电/断使能可能导致重力下垂，停止策略必须基于实物验证。

第一项控制实验是低速小范围往返跟踪，记录 q_cmd 与 q_measured 的误差、延迟、重复性和回差。轨迹幅度与速度由校准结果决定，不把“5 度”当任意初始姿态均安全的通用阈值。

### 阶段 C：相机、示教和数据集

先用一个固定外部相机，若遮挡严重再加腕部相机。有可靠夹爪则做简单抓放；没有夹爪则先做视觉到点，或确认接触条件后的低速推物。不要以更换硬件或复杂人体重定向作为首个必要步骤。

示教可从键盘/手柄受限点动开始；若需要连续演示，再选末端遥操作或主从臂。不能默认这套减速机构适合徒手拖动示教。

先记录 5–10 条，检查录像与状态对应、动作定义和回放；再用约 50–100 条成功演示启动简单任务基线。这是采集预算起点，不是成功保证；依据学习曲线、任务变化和失败类型增加数据。

验收：可以逐帧查看“看到什么、当时在哪、要求做什么、真正下发什么”；暂停/超时/重录能被标记；每条 episode 有清楚的任务与成功判据。

### 阶段 D：传统方法 + BC/ACT

先做固定目标的脚本或视觉定位+规划基线，验证硬件能完成任务。然后训练小型 BC 或 ACT；第一次只选一种，建议在 LeRobot 中先做 ACT。

5–10 条过拟合测试通过后，才扩大训练。训练损失下降并不意味着闭环成功；通过独立初始条件的实机评估判断。Diffusion Policy 作为后续对照，避免同时引入多套训练工程。

验收：留出测试 episode；同一评估配置可重复；记录成功率、人工干预、耗时、碰撞/急停、关节误差及推理延迟；失败能区分感知、策略、控制和机械原因。

### 阶段 E：一个 VLA 的适配

保留数据与控制契约，更换 policy adapter。先核对动作维度与语义，再做归一化、状态和图像映射。若原模型输出末端增量，而 Dummy 接口接收关节目标，需要 FK/IK、参考坐标系与奇异位形处理；仅改输出维度不够。

采用“离线预测→影子运行（只预测不执行）→受限闭环”。动作块包含 H 步时，先执行较短前缀再重新观察；长度由推理耗时和执行周期决定。不要把整个长动作块一次性塞满 REF 队列。

选择 VLA 的依据是数据适配难度、训练资源、推理延迟、任务语言需求和官方支持，而不是材料中谁被称为目标 backbone。

### 阶段 F：研究改进

固定基线后，每次只改变一个因素：动作平滑、空间提示、示教来源、延迟补偿或少样本适配。需要 RL 时优先仿真/离线验证奖励与故障机制；不要直接从真机随机探索开始。

MoCap 的合适位置：在可靠机器人示教基线之后，以“重定向示教是否减少真实采集量”作为独立问题。应和同样预算的机器人示教对照，并验证重定向轨迹的可达性与视觉一致性。

## 8. 数据契约：这是后续模型能否复用的关键

| 数据 | 内容与要求 |
|---|---|
| episode_id / frame_id | 稳定索引，记录任务、场景与采集批次 |
| images | RGB、相机名、分辨率、采样时间、内外参版本 |
| observation.state | 六轴实测关节状态；夹爪若无测量能力需注明 |
| action.requested | 人工/策略原始请求 |
| action.applied | 安全层处理后下发的命令，仍不等于已到位 |
| instruction | 当前任务指令，必要时对象/目标语义 |
| timing | 图像时间、反馈接收时间、命令提交时间、设备时间及同步偏移（若可得） |
| quality | 丢帧、状态年龄、限幅、重试、人工接管、终止原因 |
| metadata | 固件版本、硬件 profile、相机标定、代码提交、动作定义、实际 fps |

第一版建议明确固定 `action = 目标关节角 [+ 夹爪命令]`，以当前观测预测下一控制间隔/动作块的命令；不是笼统地把“当前关节值”同时当输入和标签。示教命令与实现后的状态都应保留，避免把执行延迟误学成策略。

原始数据保留原始时间戳，派生数据可重采样为目标 fps；记录插值方法与有效掩码。不要把录制后的未来反馈泄漏进同一时刻的观测。训练/验证按 episode、采集批次和初始布局分割，不能相邻帧随机拆分。

公共基准数据可用于软件烟雾测试，不因同为六维或七维就与 Dummy 动作兼容。动作统计量只由训练集计算，并随 checkpoint 保存。

## 9. 训练框架和资源选择

LeRobot 官方支持自定义 Robot 接口，可复用其数据采集、训练和部署工具；建议将 Dummy 封装为独立适配包，保留自己的底层 SDK，避免修改大量上游代码。[官方硬件适配指南](https://huggingface.co/docs/lerobot/en/integrate_hardware)

| 方案 | 当前用途 | 进入条件 |
|---|---|---|
| 脚本/视觉定位+规划 | 控制与任务能力基准 | 状态和受限执行可靠 |
| BC/ACT | 第一条学习基线 | 同步本机示教与可重复任务 |
| Diffusion Policy | 序列策略对照 | 已有相同数据和评估协议 |
| WALL-OSS / Wall-X | 备忘录中的 VLA 候选 | DOF、归一化、数据映射、算力测试 |
| InternVLA-M1 | 空间引导相关研究候选 | 官方实例跑通，再做本机动作适配 |
| openpi | 另一条 VLA 适配路线 | 可用显存、环境与动作定义满足要求 |

LeRobot 官方仓库包含 ACT 和 Diffusion 等实现，可把框架工作集中于适配、数据和评估，而不必先重写模型。[LeRobot](https://github.com/huggingface/lerobot)

Wall-X 官方提供 LeRobot 数据微调、机器人 DOF 配置和推理服务，当前说明还涉及 FlashAttention、自定义 CUDA 算子和独立依赖约束。建议单独建环境，不与 ROS Python 环境混装。[Wall-X](https://github.com/X-Square-Robot/wall-x)

InternVLA-M1 官方动作示例返回 normalized action chunks；返回张量不能直接写串口，需与训练配置一致地反归一化和解释动作语义。不能从 README 推断“单张 3090 一定可以微调”。[InternVLA-M1](https://github.com/InternRobotics/InternVLA-M1)

openpi 官方列出的显存估计为推理 >8 GB、LoRA >22.5 GB、全量微调 >70 GB，且说明测试环境为 Ubuntu 22.04。本机实测约 16 GB，低于该 LoRA 估计，所以不把它作为默认训练端；大型 VLA 优先在四卡服务器核实资源后试跑，不能承诺全量微调。官方数据微调入口使用 LeRobot。[openpi Requirements](https://github.com/Physical-Intelligence/openpi#requirements)

保留已安装 Ubuntu 24.04 的话，ROS 2 Jazzy 是官方对应组合；模型训练可放隔离环境/容器或独立服务器。ROS 和模型服务以显式数据接口通信，而不是强行共用同一 Python 版本。[ROS 2 官方安装说明](https://docs.ros.org/en/jazzy/Installation/Alternatives/Ubuntu-Install-Binary.html)

每个环境记录 OS、驱动、CUDA、Python、PyTorch、仓库提交和依赖锁；每个实验记录峰值显存、batch、图像数/分辨率、动作 horizon、每步耗时。先做一次前向+反向，再讨论完整训练预算。

## 10. 第一组实验如何设计

根据用户补充，首个任务建议为“固定外部 D435f 视角下，将一个轻质、易抓取物体放入固定区域”。夹爪未调通之前，先完成无接触视觉到点与夹爪独立台架测试；夹爪验收后再采抓放示教。不要把轨迹回放本身称为 VLA 实验。

| 实验 | 目的 | 输入/输出 | 主要指标 |
|---|---|---|---|
| E0 通信与状态 | 判断数据是否可信 | 查询→反馈 | 新鲜度、异常率、时延分布 |
| E1 单轴/多轴受限跟踪 | 判断控制能力 | 目标 q→实测 q | RMSE、最大误差、延迟、重复性 |
| E2 传统任务基线 | 判断任务是否机械可行 | 目标位置/视觉→轨迹 | 成功率、耗时、失败原因 |
| E3 ACT | 判断本机示教能否学会 | 图像+q→动作块 | 独立场景成功率与泛化 |
| E4 一个 VLA | 判断预训练/语言是否有收益 | 图像+指令+[状态]→动作块 | 少样本曲线、指令切换、泛化 |
| E5 单一方法改进 | 判断创新是否有效 | 同 E3/E4 | 成功率与代价指标共同改善 |

开发期可先每个条件评估约 20 次，记录成功次数和置信区间；20 次只是起点，不能支撑微小差异的稳健结论。正式比较固定初始化采样、同一数据预算，并尽可能使用多个训练随机种子。

如果研究语言能力，必须有相同或相近视觉场景下、不同指令要求不同动作的测试，例如选红色还是蓝色目标。只有单任务恒定指令，即使 VLA 成功，也不能证明语言理解贡献。

如果研究 Jerk，固定物理采样间隔、单位、滤波和任务时长；统一时间网格上可计算离散三阶差分 / Δt³。它对噪声敏感，不能把不同滤波强度的结果直接比较；同时报告成功率和耗时，防止“慢下来”冒充方法优势。0.01° 文本精度的反馈还可能放大差分噪声。

SAM2 作为可选感知模块，可比较原始 RGB、RGB+掩码、裁剪/空间提示几种输入，保持其他条件一致；先明确它解决遮挡、目标歧义还是位置泛化，不要为了增加模块而加入。

| 天 | 主任务 | 当天可检查的产物 |
|---|---|---|
| 1 | 固件/硬件画像、旧工程梳理 | 版本对应表、明确的待确认参数 |

## 12. 最先处理的五件事

1. 统一主工程文档中的 USB/REF 与 ETH2CAN/RDrive 架构冲突。

## 13. 针对现有设备的分工与夹爪接入

### 三台机器如何分工

| 设备 | 推荐角色 | 理由与边界 |
|---|---|---|
| Ubuntu + RTX 5070 | 真机 USB、D435f、示教、日志、ROS 2、ACT 部署 | 设备靠近控制端，采集与执行不依赖远程桌面；GPU 软件兼容需先验证 |
| Windows + RTX 4080 SUPER | Codex 开发、DummyStudio 对照、离线分析、备选本地推理 | 当前已实测约 16 GB；是否部署模型由延迟与显存实测决定 |
| 远端 4×RTX 6000 | 数据审计后的训练、多随机种子和模型比较 | 先确认型号/单卡显存、队列资源、磁盘和框架支持，再设 batch/并行方式 |

推荐数据流：Ubuntu 采集→检查/打包→远程训练→取回 checkpoint 与归一化配置→Ubuntu 或局域网本机推理→本地安全执行。远程桌面适合操作训练任务，不能当机器人实时控制通道。服务器可先通过现有远程桌面打开终端运行作业；只有确认已有 SSH/SFTP 或其他授权文件通道后，才设计自动提交与同步。

四张 GPU 的显存不是自动合并为一块显存：DDP 通常每卡保留完整模型；FSDP/模型并行需要框架支持且有通信开销。最开始可用单卡验证，再将四卡分别跑不同种子/配置；只有单卡容量或吞吐不足才引入分片训练。

5070 对应的新架构不能照搬旧计划的 CUDA 环境。PyTorch 2.7 起提供 Blackwell/CUDA 12.8 支持，但所选模型的 FlashAttention、自定义 CUDA 算子仍需分别验证；不要把“能 import torch”当兼容验收。[PyTorch 官方说明](https://pytorch.org/blog/pytorch-2-7/)

在 Ubuntu 与服务器各自运行只读的 `nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv`；同时记录 OS、内核、Python、PyTorch/CUDA 版本。服务器型号没有核实前不假定它是 24 GB、48 GB 或其他版本。

### 夹爪：现有源码已经提供了线索

本次找到以下实际接口：

- REF/Robot/instances/dummy_robot.h:40–42 注册 `set_angle`、`set_enable`、`set_current_limit`；第 162 行将其放入 `hand` 协议对象。
- dummy_robot.cpp:30 创建节点 7 的 DummyHand；349 行起 SetAngle 将参数裁剪到 0–30，发送 CAN 模式 0x02；366 行起电流接口裁剪到 0–1，模式 0x01。
- 已读 USB ASCII 解析器中没有对应的夹爪文本命令。`&` 的第七个参数是机械臂速度参数，**不是夹爪值**。
- 这些是历史固件的协议对象定义。它们不证明当前夹爪就是这一型号，不证明 USB 连接已启用相同 Fibre/RPC 入口，也不代表有夹爪位置/力反馈。

所以不能编造一个 `#GRIPPER` 命令直接尝试。推荐依次处理：

1. 根据夹爪标签、驱动板和接线确认：它是上述 CAN 夹爪，还是独立 PWM/串口夹爪；核对额定电源与接口。源码节点 7 仅作候选。
2. 核对当前 REF 固件是否保留相同 `hand` 对象及 USB/Fibre 服务。能枚举到兼容接口时优先复用；不能枚举时先确认固件和驱动，不先刷新整个机械臂。
3. 若只有 ASCII 通道且夹爪确属该 CAN 型号，再在匹配固件分支设计明确的夹爪文本接口，包含输入范围、ACK、超时与停止语义；先离线/台架验证。不要修改旧归档直接烧录。
4. 机械臂固定、夹爪无物体负载的条件下，按型号允许范围逐步验证开合方向、开度、限流和重复性；不照搬历史源码 0–30 为毫米，更不把电流参数理解成已知夹持力。
5. 在 Robot API 中增加独立 `gripper_command` 与能力描述。若没有开度传感器，用 command-only 标注，录像/外部测量核验开合，不能把请求值冒充实测开度。
6. 最后完成空载重复开合、轻物夹持、松开与故障恢复，然后加入抓放 episode。

具体操作命令取决于型号和当前固件，本次不提供未经证实的夹爪使能/运动指令。调试可以先完成识别和只读探测，这不妨碍相机与数据记录模块同时开发。

### D435f 如何接入

先作为固定外部相机，完整看到夹爪、物体、目标区。使用与 Ubuntu 版本、内核、设备固件匹配的 librealsense；官方支持 Ubuntu 24 系列但仍需核对具体内核，不直接照搬旧虚拟机环境。[官方 Linux 安装说明](https://github.com/realsenseai/librealsense/blob/master/doc/installation.md)

先用 RealSense Viewer 检查 RGB 和深度流是否稳定，再通过 SDK 记录 RGB、原始深度、深度尺度、内参、彩色/深度外参、帧号和时间戳。分辨率/fps 从设备实际支持的组合中选择，例如支持时以约 640×480、30 fps 作首轮候选；数据集控制 fps 由机械臂稳定反馈速度决定，不要求两者相等。

第一版 ACT 可以只用 RGB+关节/夹爪信息训练，深度先用于记录、空间标定、目标位置和高度检查；是否增加深度输入通过后续对照判断。一个 RGB-D 相机不等于有两个独立视角，模型要求多视角时不能复制同一张图假装腕部视角。

固定相机需标定 camera→robot_base 变换；RGB/深度对齐不是相机到机械臂基座标定。使用棋盘格/标记板和多姿态观测，留出未参与求解的点检查三维误差，并将误差与任务容差比较。不要用一张截图凭目测设定外参。

已有深度相机也不能省略遮挡和无效深度处理。数据中显式保存无效掩码；反光、透明物和夹爪遮挡情况下，以任务实测检验可用性。
