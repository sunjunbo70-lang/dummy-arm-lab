# v0.10 r2：GPU 常驻训练环境设计方案（2026-09-27，待审查）

- 前提：r1 的实验框架保持不变。具体包括：
  - 七操作动作契约、19 维接触参数；
  - γ=1 有限预算、时间 λ 的 GAE、势函数 Φ=-30J-10P 与终态回报；
  - G0/G1/G2 三类准入；
  - R0/R1/R2 × 3 种子矩阵；
  - 数据划分、评估与回放要求。
- r2 只改变"**环境在哪里算、怎么算**"，外加与之配套的批量参数、验收门和作业管理规则。
- 依据：
  - r1 中止分析（项目文档 `v0.10_r1中止原因分析与r2改进方案_2026-09-27.md`）；
  - 现有 `tensor_kernels.py`：压力/间隙二分求解 + CUDA Graph，batch 256 约 1.0ms，fp32 误差约 1e-5mm；
  - r1 组件：`policy.py`、`rollout.py`、`ppo.py`、`returns.py`、`actions.py`。
- 证据等级 L1。文中吞吐数字均为**估算**，必须由第 7 节的基准实测替换。

---

## 1. 目标与原则

**目标：** 把 r1 计划的训练量（开发加核心矩阵约 4500 万次高层转移）压缩到**1 天以内**完成。所需端到端吞吐为 ≥2000 转移/秒，其中已包含 PPO 更新。

**原则：**

1. **单进程、单 GPU、全张量。** 环境状态、观测、奖励、rollout 缓存、策略、优化全部常驻显存。训练主循环不经过 CPU，也不做进程间通信（v0.9 每次更新 10s 中有约 6s 花在环境和进程间通信上）。
2. **同一套物理规律，两种实现。**
   - CPU 精确参考：冻结 v8.11，多边形精确裁剪、守恒库存。
   - GPU 训练实现：规则栅格、定步长、无分支。
   - 两者用"决策一致性"门槛相互约束，不要求逐格相同。
3. **CPU 与 GPU 同时有活干。** GPU 负责训练，空闲的 CPU 核异步运行"参考求解器复核 + 完整 MuJoCo 执行复核"，专门检查策略有没有钻 GPU 近似的空子。
4. **全程定步长，没有自适应递归。** 自适应误差控制和深度递归（r1 的 v5、v8.8）属于强分支逻辑，在 GPU 上效率极差。定步长的 v8.11 路线本身就适合 GPU。
5. **先测再扩。** 任何规模扩大之前，都要有同配置的实测吞吐和预计完成时间。

## 2. 总体架构

```
┌──────────────────────── GPU（单进程）────────────────────────┐
│  BatchedWallEnv（N=1024–4096 个环境并行）                     │
│   ├─ 状态张量：墙厚[N,100,100]、刀面余料[N,6,24]、料埂[N,24]、 │
│   │   机器人/操作状态机、时间、账本（fp64 累加）               │
│   ├─ 节拍引擎 tick()：所有环境按固定物理子步同步推进            │
│   │   接近/装料/接触/续接/抬刀/检查，每种操作是若干节拍          │
│   ├─ 执行器代理：可达性/IK 查表 + 控制误差模型                  │
│   ├─ D435 代理观测（加噪、置信、梯度）→ 6×100×100               │
│   └─ 奖励/势函数/终止/自动重置                                   │
│  PPO：共享 CNN（AMP）、rollout 缓存、时间 GAE、更新             │
└───────────────┬───────────────────────────────┬──────────────┘
                │ 抽样轨迹（异步，少量）           │ 标量日志（异步写盘线程）
┌───────────────▼──────────────┐
│ CPU 复核池（14–18 个进程）    │
│  ① v8.11 精确材料重放          │
│  ② 完整 MuJoCo 机械臂执行      │
│  ③ 独立评估回合                │
└──────────────────────────────┘
```

**不迁移到 GPU 的部分：** 完整 MuJoCo 机械臂动力学、v8.11 精确求解器、原生回放渲染。它们只用于复核、评估和最终交付。

## 3. 核心设计一：节拍引擎（解决半马尔可夫变长动作的批量化）

**难点：** 一个高层动作的物理时长从 0.5 秒（检查）到几十秒（26cm 长刀或 4 段续接）不等。如果按"动作"来批量处理，短动作要等长动作，GPU 大量空转。

**做法：** 把环境改成**固定物理子步的节拍机**。
- 每个环境有一个操作状态机，用整型张量表示：`op`、`phase`、`progress`、`segment_idx`。
- 每次 `tick()`，所有环境都推进一个子步。执行接触的环境做材料计算，其余环境做对应的运动或计时，都用 mask 张量区分。
- 动作结束的环境设置 `need_decision=True`。
- 主循环：
  1. 反复 `tick()`，直到有足够多的环境需要决策（例如 ≥25% 的环境，或每 K 拍一次）；
  2. 对**需要决策的子集**批量运行一次策略前向；
  3. 写回动作，继续 tick。
- rollout 缓存按决策写入扁平数组，记录环境编号和决策序号。GAE 在 GPU 上按环境分段做反向扫描。r1 的 `rollout.py` 已经把展平、时间 GAE 和整批归一化做好了，这里只需改成接收不定长输入。
- 目标：空转比例（完成动作后在等待的环境/总环境）<15%，作为验收指标记录。

**子步长：**
- 接触相位按路径弧长定步长，由第 6 节的分辨率-成本扫描确定。预计 0.25–0.5mm，r1 v8.11 用的是 50μm。
- 非接触相位（接近、装料、抬刀、检查）不需要材料积分，按真实耗时**直接跳过时间**，只累计时钟。这些相位不占用材料计算的子步。

## 4. 核心设计二：GPU 材料物理

状态布局（每个环境）：
- 墙面厚度：100×100（5mm 格，50×50cm 计算域），fp32；
- 刀面余料：6×24（3cm×12cm，5mm 格）；
- 刀前料埂：24；
- 账本：新料、墙、刀、料埂、回收、掉落、域外，fp64，只做累加。

每个接触子步的内核序列（目标是融合成 3–5 个内核，或者整段捕获成一个 CUDA Graph）：

1. **刀面足迹栅格化。** 刀面是旋转矩形，用每格 4×4 的超采样计算覆盖率，得到 `[N,100,100]` 中的一个局部窗口（约 30×30）。
   - 这一步替代 v8.11 的多边形精确裁剪，没有分支，天然并行；
   - 误差由第 6 节的门槛约束，超采样倍数可调（2×2 / 4×4 / 8×8）。
2. **间隙求解。** 复用 `tensor_kernels.solve_gap` 的物理（屈服应力挤压承载 = 法向力）。
   - 20 次二分改为**以上一子步的间隙作初值、做 2–4 次保护牛顿或二分**，因为相邻子步的间隙变化很小；
   - 预计该内核耗时降到原来的 1/5。
3. **挤出与交换。** 沿用 v8.11 已验证的**处理顺序**：沉积/拾取过程中就按墙面承载上限截断，而不是步末截断。这正是 r1 中把误差降低 146 倍的那处修正，GPU 版本必须保持相同顺序。
   - 用 gather/scatter 在局部窗口内完成；
   - 为了可复现，scatter 采用"排序 + 分段求和"的确定性模式，另设一个非确定性的快速模式供训练使用。
4. **料埂推移与刀尾沉积。** 按列更新料埂。
5. **守恒与合法性。**
   - 每个子步检查非负性，对负值做截断并计入 `clip_residual` 账；
   - 每个动作结束时检查账本闭合，在 fp32 下相对误差 ≤1e-6；
   - 违规的环境打上 `invalid` 标记并重置，同时记入日志。**不静默吞掉错误。**

抬刀分配（`lift_wall_fraction`）、坍落、搬运损失、刀面余料的搬运物理照搬 r1 公式，写成张量操作。

**显存估算：** 每个环境约 0.3MB（含局部窗口的临时量），4096 个环境约 1.2GB。加上 rollout 缓存（32k 个观测 × 6×100×100 × fp16 ≈ 3.9GB）和网络，16GB 的 RTX 4080 SUPER 足够。

## 5. 核心设计三：GPU 执行器代理（替代训练时的 MuJoCo）

r1 的连续接触执行器和 G1 验证都还没完成。r2 把执行器拆成**离线标定 + 在线查表**：

1. **可达性与 IK 张量表**（离线在 CPU 上用 MuJoCo 计算一次，存为 `.pt`）：
   - 维度：墙面坐标 u、v（5mm）× 刀向 ψ（15°）× 倾角（5°）；
   - 存储内容：可达标志、关节解（主分支）、到关节限位的余量、腕部奇异度量。
   - 在线用三线性插值查表。沿路径采样时，检查关节解是否连续（相邻采样点的关节跳变是否超过阈值），以及限位余量。
   - 不可达的动作按 r1 规则成为**带原因的真实转移**，同时扣除耗时。
2. **控制误差模型**（离线用 MuJoCo 标定，用于随机化）：
   - 实际法向力 = 增益 × 指令 + 滞后 + 噪声。v0.8 实测的增益约 1.8 倍，要按力、倾角、速度分档拟合；
   - 跟踪误差（按速度和曲率分档）；
   - 搬运掉料率（联合仿真 15–21%，按余料量和姿态拟合）。
   - 训练时在标定值附近随机化，覆盖可达表与联合仿真之间的差距。**这一项是 v0.5–v0.9 可达表训练最大的教训，必须补上。**
3. **标定数据来源：** 在 CPU 池上用完整 MuJoCo 跑约 1000 条分层抽样的接触路径（覆盖短/中/长、续接、各方向），并行约 1–2 小时，产出 `controller_contract.json` 和误差模型参数。

完整 MuJoCo 的 GPU 化（MJX / MuJoCo Warp）作为**后续选项**，本版本不做。原因：墙面接触加自定义材料的耦合移植工作量大，而查表加误差模型已经能覆盖训练需要，最终再由原生 MuJoCo 评估兜底。

## 6. 数值验收：GPU 实现与 CPU 参考的等价门

在 r1 固定的 **100 个单段 + 50 条 × 100 动作**集合上执行。输入完全相同：同初态、同动作、预生成的同一份噪声。

| 项目 | 门槛 | 说明 |
|---|---|---|
| 守恒 | 账本闭合相对误差 ≤1e-6，无负值、无 NaN | 硬门槛 |
| 决策一致性 | 单动作 ΔJ 符号一致率 ≥95%；同初态 8 个候选动作排序的 Spearman ≥0.9 | 主判据：保证 GPU 奖励不误导学习 |
| 量值 | 墙厚 RMSE 差 ≤0.05mm；|ΔJ| 差 ≤0.005；覆盖率差 ≤0.5 个百分点 | 约为传感器噪声的 1/12 |
| 序列累积 | 100 动作后 RMSE 差 ≤0.1mm，最终 J 相对差 ≤3% | 检查误差是否随步数发散 |

**同时扫一条"分辨率-成本"曲线：**
- 子步间距 0.1/0.25/0.5/1.0/2.5mm × 超采样 2×2/4×4；
- 选出**满足上表门槛的最便宜组合**，冻结后写入 `physics_gpu_v1`。

不满足时，先按超差项定位（足迹、间隙、交换、抬刀，逐阶段比较，r1 的分阶段对照工具可以复用），**不放宽门槛，也不改用 CPU 训练**。

**训练期复核：**
- 每 16 次更新，从当前策略的 rollout 中分层抽 32 条完整接触串，交给 CPU 池用 v8.11 重放；
- 每 64 次更新，抽 8 条交给完整 MuJoCo 执行；
- 复核指标超过上表门槛 2 倍时，自动暂停并报警。这是"策略在钻 GPU 近似的空子"的信号。

## 7. 吞吐目标与基准

**需求推算：**

| 训练量 | 转移数 | ≥2000/s 时耗时 | ≥5000/s 时耗时 |
|---|---:|---:|---:|
| 超参筛查（4 配置 × 32 更新） | 1.05M | 9 分钟 | 3.5 分钟 |
| 开发 2 种子 × 128 更新 | 2.10M | 18 分钟 | 7 分钟 |
| 核心 R0/R1/R2 × 3 种子 × 512 更新 | 37.7M | 5.2 小时 | 2.1 小时 |
| 核心扩展到 1024 更新 | 75.5M | 10.5 小时 | 4.2 小时 |

**粗略估算（待实测）：**
- 以 0.5mm 子步、平均 12cm 接触计，每个接触动作约 240 个子步；
- 如果每个子步在 N=2048 下融合后耗时约 1–2ms，一个接触动作批次约 0.25–0.5 秒，折合 4000–8000 个接触动作/秒；
- 非接触动作接近免费；
- PPO 更新（32k 样本 × 4 个 epoch，小 CNN，AMP）预计 3–6 秒。
- 端到端 2000–5000 转移/秒是合理区间。

**基准协议**（沿用 r1 第 12 节）：
- 批量 N = 64 / 256 / 1024 / 2048 / 4096，每档 3 次 × ≥120 秒，预热时间单列；
- 固定混合负载：装料、短/长接触、续接、抬刀、检查、结束；
- 分项计时：足迹、间隙、交换、观测、策略前向、GAE、优化、日志；
- 最后跑 50 次真实 PPO 更新的端到端计时。
- 放行条件：端到端 ≥2000 转移/秒，并且第 6 节等价门通过。未达标时，按分项计时定位瓶颈，不进入矩阵。

## 8. PPO 配置调整（因批量变大）

| 项 | r1 | r2 | 理由 |
|---|---|---|---|
| 每次更新的转移数 | 8192（64 环境 × 128） | 32768（2048 环境 × 约 16 决策） | GPU 批量更大；总转移数不变，更新次数相应减为 1/4 |
| 正式预算 | 512 更新 × 8192 = 4.19M/种子 | 128 更新 × 32768 = 4.19M/种子 | **按转移数对齐**，保持 r1 的比较口径 |
| minibatch | 512 | 4096 | 与批量同比例放大 |
| epoch / clip / KL 门限 | 4 / 0.1 / 0.03 | 不变 | — |
| 学习率 | 1e-5（候选 3e-6/1e-5/3e-5） | 在开发筛查中重新选 | 批量变大后最优学习率会变 |
| 混合精度 | — | CNN 用 AMP：4080 用 bf16；服务器 Turing 用 fp16 + GradScaler | 物理保持 fp32，账本 fp64 |
| 覆盖率约束 | ≥80% 的环境片段覆盖完整接触串 | 相同；每环境决策数 16 不够时增加到 32，同时减少环境数 | 保持时间信用分配的质量 |

**里程碑换算：** r1 的"每 32 更新验证、128 更新观察点、512 更新决定是否扩展"，统一按**累计转移数**换算，即 262k / 1.05M / 4.19M 转移，不按更新次数。

## 9. 软件与平台选择

- **状态容器与 PPO：** PyTorch 2.8 + CUDA 12.8（已安装）。
- **自定义内核：**
  - 首选：PyTorch 张量操作 + CUDA Graph 捕获整段接触子步循环。现有 `CapturedGap` 已验证这条路可行，Windows 原生可用。
  - 如果内核数量过多、启动开销占主导，再用 **NVIDIA Warp** 写融合内核。Warp 官方支持 Windows，与 PyTorch 通过 DLPack 零拷贝互通。
  - 如果改在 Linux 上训练（WSL2 或 Ubuntu 机器），可以用 `torch.compile` / Triton 自动融合。Triton 在 Windows 上没有官方支持，不建议在原生 Windows 上依赖它。
- **多卡：** 中央服务器 4 × RTX 6000（Turing，24GB）适合**3 个种子各占一张卡并行**，比单卡串行快约 3 倍。注意 Turing 不支持 bf16，需要改用 fp16。本地 4080 SUPER 用于开发和基准测试。
- **解释器：** 统一使用 `.venv-loop`，启动时自检 torch/CUDA/numba/warp 版本，写入 manifest。

| S8 核心矩阵 | R0/R1/R2 × 3 种子；每 1.05M 转移验证一次，4.19M 时按 r1 规则决定是否扩展 | 按实测推算（预计 3–6 小时，服务器三卡并行更快） | 按 r1 第 14 节评估，包括原生 MuJoCo 24 → 80 场 |

- 工程量约 8–10 个工作日，其中计算时间很少，绝大部分是开发。
- **S5 之前不启动任何长时间计算**，S2 的 CPU 补跑除外，且有明确上限。

## 11. 作业管理规则（吸取 r1 教训）

1. 任何 >30 分钟的计算，启动前写 manifest：要回答的问题、单位成本 × 数量 = 预计耗时、停止条件、解释器、设备。实际耗时超过预计 2 倍，或 30 分钟没有新产出，就自动暂停并通知。
2. 同一时刻只运行 1 个主任务，外加 CPU 复核池。新版本启动前，停掉并归档旧任务。
3. 自动跟进的目标写成"在 X 小时内交付阶段 Sk"，而不是"让某门槛通过"。同一阶段连续 3 次失败时，必须停下来汇报选项。
4. 监控绑定任务组。GPU 记录利用率、显存、功耗；CPU 按进程树记录。报告中写**有效转移/秒**，不以"占用率高"为目标。
5. 每个阶段结束写一页记录：做了什么、实测数字、是否通过、下一步。

## 12. 风险与对策

| 风险 | 对策 |
|---|---|
| 栅格化足迹的精度达不到等价门 | 提高超采样倍数；只对局部窗口精细化；仍不行，再在 GPU 上实现解析平移边界核（r1 已推导，无分支，可以移植） |
| 策略利用 GPU 近似或执行器代理的漏洞 | 训练期复核（第 6 节）加原生 MuJoCo 评估；超差自动暂停 |
| 空转比例高（动作长短悬殊） | 按接触长度分桶调度；增加每环境决策数；非接触相位直接跳时 |
| 续接、抬刀状态机在张量化后出错 | S4 用 CPU 参考逐步对拍 100 条多段序列；状态机转移表单元测试 |
| fp32 守恒误差累积 | 账本 fp64 累加；每动作做闭合检查；负值截断单独记账 |
| Windows 工具链限制 | 以 CUDA Graph + Warp 为主；必要时转到 WSL2 或服务器 |
| 开发周期超出预期 | 每阶段设时长上限；超出时汇报并由用户决定，不自动无限推进 |

## 13. 与 r1 的对照（哪些改、哪些不改）

| 保持不变（r1 框架） | 改变（r2） |
|---|---|
